# IKEA table assembly — 실험 기록

대상: `carroll511/IKEA_table_assembly` (G1 + Dex1, `teleop_ikea.py` 녹화, 제자리 양팔 조립)
자매 실험: `examples/unitree_g1_dex1_bct/EXPERIMENTS.md` (BCT 데이터셋). 레시피 대부분을 여기서 가져왔다.

---

## 0. 데이터셋

| | |
|---|---|
| 원본 | LeRobot **v3.0**, 276 ep / 66,600 frame @ 30 fps = 37분 |
| 서브태스크 | `pick table leg` 77ep · `insert table leg to table base` 72ep · `rotate leg to tighten` 127ep |
| 카메라 | `cam_left_high` `cam_right_high` `cam_left_wrist` `cam_right_wrist` — 640×480 AV1, 4개 모두 정확히 66,600 프레임 |
| state / action | 86차원(18블록) / 19차원(5블록) |

### 확인된 사실

- **`base_cmd_vel` 3차원이 전 프레임 정확히 0** (std 0.000000). 로코모션 미사용 → action에서 제외.
  정규화 시 q01=q99가 되어 0으로 나눈다.
- **action에 waist가 없다.** `teleop_ikea.py`는 팔만 명령하고 waist는 시작 자세 유지(에피소드 내 0.09~0.45°).
- **legs도 거의 안 움직인다** (에피소드 내 0.73°). 제자리 작업.
- **스톨이 이미 제거돼 있다** (|Δarm| < 1e-4가 0.07%). BCT에서는 직접 청소해야 했다.
- **타이밍이 완벽하다.** dt 33.333ms 고정, gap 0, frame_index 불연속 0.
- **action-state lag는 2~3프레임**(1.05°). IK+제어 지연으로 정상.
- **`left_eef`/`right_eef`는 같은 행 관절의 FK이고 lag이 0이다.**
  `FK(arm_q[t], waist=0)` vs 저장값 오차 **4.2e-09 m** (lag ±1에서는 6e-4).
  BCT의 기록 ee_state가 10프레임 지연이라 재계산해야 했던 문제가 여기엔 없다.
  URDF sha256 `8bbf0066…c238735`가 로컬 파일과 일치, 배포 코드 `G1WristKinematics`가
  **1.5e-08 m / 5.9e-08 rad**로 재현.
- **스테레오 좌우 명명이 맞다.** `cam_left_high`의 특징점이 `cam_right_high`보다 오른쪽에 찍힘
  (15개 샘플 전부 같은 부호). BCT에서 cam_0/cam_1이 뒤집혀 있던 것과 달리 이름을 믿어도 된다.

### 원본 데이터셋이 이미 적용한 필터

`modality.json`의 `_ikea.notes.filters`에 기록돼 있다. **우리 변환은 아무것도 버리지 않는다**
(276 ep / 66,600 frame 손실 0, state/action 바이트 동일).

| 필터 | 값 |
|---|---|
| `head_trim_s` | 2.0 (녹화 앞 2초 삭제) |
| `min_static_run` / `static_eps_rad` | 15 / 1e-6 (텔레옵 스톨 제거) |
| `max_ik_residual_mm` | 20.0 |
| `require_motion_data_ready` | True |
| `min_segment_len` | 40 (horizon과 같음 — 이보다 짧으면 윈도우 0개) |
| `max_frame_gap_ratio` | 2.5 |
| `drop_unlabeled` | True |

필터를 바꾸려면 원본 녹화에서 `convert_ikea_json_to_lerobot.py`를 다시 돌려야 한다.
HF 데이터셋만으로는 잘린 부분을 되살릴 수 없다.

## 1. 변환과 분할

`convert_ikea_v3_to_v2.py` — v3.0 → v2.1 순수 재배치.

**영상은 재인코딩한다(stream copy 아님).** 소스가 AV1 GOP 2라 copy는 홀수 프레임에서 시작하는
에피소드를 앞 키프레임으로 당긴다. **276개 중 146개가 홀수 시작**이라 절반 이상이 조용히
1프레임 어긋났을 것이다. `-ss` + `-frames:v`로 자르면 프레임 정확하고, GOP 2라 비용은
카메라당 1패스 수준. 검증: 144프레임 픽셀 비교 최대 오차 1.7/255.

### val은 세션 단위로 뺀다

연속 에피소드는 같은 촬영 세션(발 위치·헤드 틸트 동일)이라 **랜덤 분할하면 val이 학습 이웃과
거의 중복돼 과적합을 못 잡는다.** 발 위치와 헤드 틸트가 동시에 점프하는 지점으로 27개 세션을
검출하고(`sessions.json`), 그중 4개(3, 12, 19, 23)를 통째로 뺐다.

| | ep | frame | 비율 |
|---|---|---|---|
| train | 250 | 59,589 | 89.5% |
| val | 26 | 7,011 | **10.5%** |

태스크별 val 비율 9.9~11.3%로 균형. 헤드 틸트가 ep85에서 ~7°→~16°로 바뀌는 두 리그 구성이
있는데 양쪽 모두 포함시켰다 (train 4.4~17.6° / val 5.3~17.6°).

## 2. 확정 레시피

BCT 최종본을 그대로 가져오되 **스케일만** 바꿨다.

| | 값 | 근거 |
|---|---|---|
| 뷰 | 3 (`cam_left_high` + 양 손목) | BCT 뷰 개수 ablation에서 4번째 뷰가 팔 정확도 변화 0.00% |
| state | 46차원 9키 | BCT 46차원 키가 이름·차원 그대로 전부 존재 |
| action | **16차원** — 팔 7+7 REL, 그리퍼 1+1 ABS | waist 없음, `base_cmd_vel` 제외 |
| horizon | 40 = 1.33s @30Hz | BCT 검증값. 배포는 앞 8스텝만 실행 |
| **effective batch** | **64** (global 16 = 8/GPU × accum 4) | CK-Sung 실배포 선례(17k프레임/eff 64) |
| max_steps | 20,000 = 25.7 epoch | 아래 3번 |
| save_steps | 2,000 | 스캔용 |
| lr / scheduler | 1e-4 / cosine, warmup 0.05 | 저장소 기본 |
| weight decay | 1e-5 | 기본 |
| state_dropout | 0.2 | BCT 검증값 |
| color jitter | 0.3 / 0.4 / 0.5 / 0.08 (기본값) | 아래 5번 |

학습 데이터: 250 ep / 59,589 frame / **49,839 horizon-40 윈도우** → eff. batch 64에서 **779 step/epoch**.

배치가 64인 이유: 60k 프레임에서 192면 epoch당 260스텝, 256이면 195스텝뿐이다.
BCT(500k)에서는 이 문제가 없어 192를 썼다.

## 3. GPU 수 — 2장이 4장보다 빠르다 ✅ 확정

effective batch 64 고정, 각 30스텝 측정 (s/step, 정상 구간):

| 구성 | bf16 통신 없이 | **`--ddp-comm-bf16`** |
|---|---:|---:|
| 1 GPU (micro 8 × accum 8) | 2.46 | — |
| **2 GPU (global 16 × accum 4)** | 1.55 | **1.46** ← 최적 |
| 4 GPU (global 32 × accum 2) | 3.98 | 2.24 |

배치를 고정하면 GPU를 늘려도 스텝당 일이 늘지 않고 같은 64샘플을 더 잘게 쪼갤 뿐인데,
1.62B 파라미터 all-reduce는 스텝당 한 번 그대로 들고 피어가 늘수록 비싸진다.
이 호스트는 NVLink가 없어 PCIe/SYS를 탄다.

**bf16 압축이 2 GPU에선 6% 이득인데 4 GPU에선 44%**인 것이 통신 병목의 결정적 증거다.
워커를 16→8로 줄여도 4 GPU는 3.98→3.95라 CPU 경합이 아니다.

→ **남는 GPU는 병렬 ablation에 쓴다.** 2 GPU 런 3개를 동시에 돌려도 1.43~1.45 s/it로
속도 저하가 없었다 (96코어에 워커 32+20+20).

**항상 `--use-ddp --ddp-comm-bf16`을 붙일 것.**

## 4. 체크포인트 선정 — eval_loss 쓰지 말 것

BCT에서 확립된 것과 동일. `eval_loss`는 랜덤 노이즈 레벨에서의 flow-matching 회귀 목적함수라
액션 품질을 추적하지 않는다. 대신 `scan_ikea.py`로 open-loop 스캔한다.

**stride를 10으로 낮춘다.** `eval_val_mse.py`의 기본은 stride=horizon(비중첩)이라 이 val에서
윈도우가 164개뿐인데, 체크포인트 간 차이가 1~2%라 노이즈에 묻힌다. stride 10이면 **614개**.
윈도우가 겹쳐 독립 표본은 아니지만, 모든 체크포인트를 **동일한 고정 세트**에 윈도우별 고정
diffusion seed로 채점하므로 *비교*에는 충분하다.

### 노이즈 대역 (baseline 자신의 16k/18k/20k 편차)

| 지표 | 편차 |
|---|---|
| MSE | **2.02%** |
| 팔 | 0.36% |
| EE8 | 0.94% |
| 그리퍼 | 4.87% |

**이보다 작은 차이는 차이가 아니다.** 이 표가 아래 모든 판정의 기준이다.

### ⚠️ MSE는 action 차원이 다르면 비교 불가

19차원 런(waist 포함)의 MSE는 16차원 런과 직접 비교할 수 없다. waist가 거의 상수라 예측이
쉽고, 그 3차원이 평균에 섞여 MSE를 **희석**시킨다. C3 vs baseline의 "MSE −12.8%"가 그 예로,
팔·EE8·그리퍼는 오히려 전부 나빠졌다. **차원이 다르면 팔·EE8·그리퍼로만 비교할 것.**

## 5. 기각된 ablation ❌

모두 20k, effective batch 64, 다른 변수 동일. 기준은 baseline @20000
(MSE 0.02870 / 팔 2.895° / EE8 10.62mm / 그리퍼 0.1290).

| 실험 | 결과 | 판정 |
|---|---|---|
| **`torso_gravity` 추가** (state 46→49) | MSE +5.4%, 팔 +0.8%, EE +1.0%, EE8 +1.7%, 그리퍼 +0.5% — **전 지표 열세** | ❌ |
| **color jitter ×0.5** | MSE +0.6%, 팔 +0.6%, EE8 +2.4% — 노이즈 내 | ❌ |
| **웜스타트 연장** (20k→30k) | 22k에서 MSE **+10.5% 열화**, 회복에 6,000스텝, 최종 배포지표 +0.1% | ❌ |
| **새 30k cosine** | 24k 지점이 baseline과 MSE 동률, 팔·EE8·그리퍼 1~3% 열세 | ❌ |
| **태스크 재밸런싱** | 미실시 — 아래 근거로 불필요 | ❌ |

### `torso_gravity`가 실패한 이유 (사전 예측과 일치)

처음엔 "헤드 카메라 자체 기울기이고 BCT엔 없던 신호"라고 판단했으나 **틀렸다.**
몸통 기울기는 waist **pitch**(범위 10.87°)에서 오는데 그건 이미 `waist`에 있다.
`base_gravity` + `waist`로 회귀하면 **R² 0.9985, 잔차 평균 0.15° / 최대 0.66°**
(전체 스프레드 15.1° 대비). 새 정보가 아니라 중복 3차원이었다.
BCT에서 FK EE가 "정보량 0의 재파라미터화"였던 것과 같은 함정.

배포 가능 여부와는 별개다 — 대회 boundary는 torso IMU를 안 주지만 `base_quat` + `waist`로
복원되므로 만들 수는 있다. 다만 만들 이유가 없다.

### color jitter — 세기가 성능과 무관하다

frozen 인코더(`tune_llm=False`, `tune_visual=False`) 특징이 augmentation으로 얼마나 움직이는지
측정했다. "서로 다른 에피소드 프레임 간 거리"를 100%로 두면:

| 변형 | 기준 대비 |
|---|---:|
| 랜덤 크롭 89.8%만 (기본) | 57.0% |
| **컬러 지터 ×1.0만 (기본)** | **64.5%** |
| 컬러 지터 ×1.5만 | 78.0% |
| 컬러 지터 ×3.0만 | 139.2% |
| **크롭 + 지터 ×1.0 (현재 전체)** | **78.1%** |

인코더는 색 변화에 **전혀 robust하지 않다** — 기본 설정만으로도 특징이 자연 변동의 64.5%만큼
움직인다. 그런데 세기를 절반으로 줄여도 성능이 노이즈 내에서 안 변했다.
→ **action expert가 시각 특징 노이즈에 병목이 걸려 있지 않다.** 강화도 약화도 의미 없으니
기본값을 쓴다. (이건 VLM 튜닝의 기대치를 낮추는 간접 증거이기도 하다.)

### 웜스타트가 실패한 이유

이 런들은 `--save-only-model`로 저장하므로 `optimizer.pt` / `scheduler.pt` / `rng_state.pth`가
**없다.** 게다가 완주한 cosine은 LR을 ~1e-12까지 소멸시킨다. 그대로 재개하면 스케줄러가
새 max_steps 기준으로 재생성되어 **LR이 2.7e-5로 점프**하고 Adam 모멘트는 0에서 시작한다.
LR을 2e-5로 낮춰 통제해도 22k에서 10.5% 열화를 겪었다.

→ **긴 스케줄이 필요하면 처음부터 그 길이로 돌릴 것.** 이어붙이지 말 것.

### 태스크 불균형은 원인이 아니다

학습 윈도우 비율: `rotate` 49.8% / `insert` 28.2% / `pick` 22.0% (최대/최소 2.26배).
BCT는 재밸런싱해서 1.20배였다.

그런데 baseline @20000의 태스크별 성능은:

| 태스크 | 윈도우 | 팔 | EE | EE8 | 그리퍼 | 손목 이동 | EE/이동 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `pick table leg` | 142 (22.0%) | **2.585°** | **16.57** | **8.16** | 0.1845 | 44.2 | **0.38** |
| `insert table leg to table base` | 179 (28.2%) | **2.447°** | 16.59 | 11.66 | **0.1065** | 32.0 | 0.52 |
| `rotate leg to tighten` | 293 (49.8%) | 3.318° | 21.05 | 11.17 | 0.1158 | 50.6 | 0.42 |

**학습 비중이 가장 낮은 `pick`이 팔·EE에서 가장 좋고, 가장 높은 `rotate`가 가장 나쁘다.**
데이터 양이 아니라 과제 난이도가 지배한다 → 재밸런싱할 근거 없음.
60k에서 27%를 버릴 이유가 없다.

`insert`는 EE/이동거리 비가 0.52로 가장 나쁘다 — 손목이 32mm 움직이는 동안 16.6mm를 틀린다.
정밀 삽입이 실제로 제일 어렵다는 것이 수치로 확인된다.

## 6. 스텝 수 — 팔/EE는 16k에 포화, 그리퍼만 계속 개선 ✅ 확정

baseline 16k → 20k 변화:

| 지표 | 변화 |
|---|---|
| 팔 | −0.35% (정지) |
| EE | −0.17% (정지) |
| **그리퍼** | **−4.64%** (개선 중) |
| MSE | −1.98% (대부분 그리퍼 기여) |

그리고 20k를 넘기려는 두 시도(웜스타트, 새 30k)가 모두 실패했다(5번).
→ **20,000이 이 데이터셋의 상한에 가깝다.**

> ⚠️ **정정 (2026-08-24).** 그 "30k 런"은 완주하지 못했다. 디스크가 찼을 때 26k 부근에서
> 죽어 24000이 마지막 체크포인트이고, 12k~24k만 스캔됐다. 즉 **끝까지 anneal된 30k 모델은
> 측정된 적이 없다.** 남은 근거는 스케줄이 다른 두 런의 같은 스텝 비교다: 20000에서
> 30k 스케줄 10.85 vs 20k 스케줄 **10.66**, 24000에서 10.94 (이 시점 LR은 이미 peak의
> ~10%까지 내려와 있다). 여전히 30k에 불리한 근거이지만 "완주해서 졌다"는 아니다.

### 배포 관점 정확도 (baseline @20000)

| 실행 스텝 | 재추론 주기 | 팔 | **EE 위치** |
|---|---|---|---|
| 1 | 0.03 s | 0.80° | 7.99 mm |
| 5 | 0.17 s | 1.39° | 11.06 mm |
| **8** | **0.27 s** | **1.80°** | **13.14 mm** |
| 16 | 0.53 s | 2.67° | 17.65 mm |
| 40 (전체) | 1.33 s | 4.33° | 25.85 mm |

앞 8스텝 **평균**은 팔 1.311° / EE 10.62mm. 첫 스텝부터 8mm인 것은 학습 한계라기보다
flow-matching 4-step 추론의 바닥으로 보인다 (미검증).

## 7. BCT 사전학습 — ⚠️ **부분적, 결론 유보** (부호 일관성은 §12에서 해소)

> v2 데이터셋 재실험에서 팔·EE8의 부호가 일관되게 나왔다. 아래 "애매한 것" 중
> **부호가 엇갈린다**는 부분은 §12로 갱신됐다. 나머지(n=1, 해석 미확정)는 유효하다.

BCT 최종 배포 모델(`RooibosT/gr00t-n1.7-g1-dex1-bct-relarm-aug-30hz-h40`,
라운드2 ckpt-15000, eff. 192 / 15k)에서 웜스타트하면 나아지는가?

**동기**: IKEA의 태스크 문자열 3개가 BCT 5개의 **정확한 부분집합**(글자 단위 동일)이고,
state 46차원 9키가 이름·차원 그대로 같으며, 시각 격차도 작다 (frozen 인코더 특징 거리:
IKEA↔BCT가 IKEA 내부 편차의 1.33~1.47배). BCT는 8배 크다 (500k vs 60k).

**설계**: action 슬롯 정렬 교란을 분리하기 위해 2×2로 돌렸다. BCT는
`[waist3|left_arm7|right_arm7|grip|grip]` = 19차원을 출력하므로, IKEA를 16차원으로 두면
모든 팔 슬롯이 3칸 밀린다. `make_waist_action_variant.py`로 waist를 앞에 붙인 19차원 변형을
만들어 정렬본을 준비했다 (waist는 명령값이 없어 같은 행의 측정 waist를 쓴다).

### 결과 — 16k/18k/20k 평균 ± 표준편차

| 런 | init | action | 팔 (deg) | EE8 (mm) | 그리퍼 |
|---|---|---|---:|---:|---:|
| baseline | base | 16d | 2.900 ± 0.004 | **10.66 ± 0.04** | 0.1314 ± 0.0028 |
| C3 | base | 19d | 2.938 ± 0.012 | 10.78 ± 0.08 | 0.1317 ± 0.0007 |
| C1 | **BCT** | 16d | 2.904 ± 0.007 | 10.74 ± 0.01 | **0.1235 ± 0.0032** |
| C2 | **BCT** | 19d | 2.905 ± 0.005 | 10.76 ± 0.02 | **0.1228 ± 0.0009** |

### ✅ 확실한 것

**1. action head 슬롯 정렬은 최종 성능에 영향이 없다.** C2 vs C1 (BCT init 고정):

| 지표 | 차이 | 노이즈 | 판정 |
|---|---:|---:|---|
| 팔 | −0.03% | 0.30% | 동률 |
| EE8 | −0.21% | 0.21% | 경계 |
| 그리퍼 | +0.56% | 2.71% | 동률 |

초기 loss는 정렬 0.31 vs 어긋남 0.62로 **2배** 차이였는데 20k에서 완전히 수렴했다.
사전학습 이득은 action head가 아니라 그 앞단(state 인코더·백본 어댑터·DiT)에서 오고,
action head는 어차피 처음부터 다시 학습된다.

→ **BCT를 16차원으로 재학습할 필요가 없다.** 정렬을 위해 waist를 끼워 넣을 필요도 없다.

**2. 그리퍼가 −6% 개선되고, 이것은 두 번 독립적으로 재현된다.**

| 비교 | 그리퍼 | 변화량 vs 노이즈 |
|---|---:|---|
| C1 vs baseline (16차원끼리) | **−6.0%** | 0.0079 vs 0.0042 → 유의 |
| C2 vs C3 (19차원끼리) | **−6.7%** | 0.0089 vs 0.0011 → 유의 |

서로 다른 action 공간, 서로 다른 학습 런에서 같은 크기로 나온다.

### ⚠️ 애매한 것 — 그래서 결론을 유보한다

**팔과 EE8에는 이득이 없고, 오히려 나빠진 신호가 있다.**

| 비교 | 팔 | EE8 |
|---|---:|---:|
| C1 vs baseline (16차원끼리) | +0.1% (노이즈 내) | **+0.8% (유의, 악화)** |
| C2 vs C3 (19차원끼리) | −1.1% (유의, 개선) | −0.2% (노이즈 내) |

**두 비교의 부호가 서로 반대다.** 팔은 한쪽에서 개선, 다른 쪽에서 노이즈 내.
EE8은 한쪽에서 **악화**(유의), 다른 쪽에서 노이즈 내. 일관된 방향이 없다.

배포에서 실제로 실행하는 구간이 EE8이므로, 이건 무시할 수 없는 불확실성이다.

**추가로 유보하는 이유:**

- **n=1이다.** 소스 데이터셋 하나(BCT), 타깃 하나(IKEA), 시드 하나. 다른 데이터셋 쌍에서
  같은 결과가 나온다는 근거가 없다.
- **MSE 수치를 신뢰하지 말 것.** C2의 "MSE −21.2%"는 그리퍼 실개선과 waist 희석이 겹친 값이다.
  19차원과 16차원의 MSE는 비교 불가다 (4번 경고 참조).
- **그리퍼 −6%의 해석이 미확정.** BCT가 같은 3개 태스크를 500k 프레임으로 봐서 파지 타이밍을
  배웠다는 것이 자연스러운 설명이나, 검증하지 않았다. 언어 조건부가 같은 문자열이라
  모드 매칭이 쉬웠을 가능성도 있다.

### 현재 판단

**그리퍼 −6% vs EE8 +0.8%의 맞교환이다.** 둘 다 노이즈 밖이라 진짜 트레이드오프이고,
어느 쪽이 나은지는 실기에서 무엇이 먼저 실패하느냐에 달렸다. 지표만으로 결정할 수 없다.

- 파지 유지가 중요한 작업(`insert`, `rotate`)이 많다면 → C1
- 팔 정밀도 우선이면 → baseline

**다른 데이터셋으로 옮길 때는 이 실험을 다시 해야 한다.** 여기서 "BCT 사전학습이 좋다"를
일반화하지 말 것.

## 9. 운영 메모

### 디스크

체크포인트가 **12GB/개**다. `--save-only-model`이어도 3.14B 전체 모델을 매번 쓴다.
20k/2k 런 하나가 120GB를 먹고, 5개 런을 동시에 돌리면 디스크가 조용히 찬다.
**첫 증상은 몇 시간 뒤 저장 중 `SafetensorError: No space left on device`로 런이 죽는 것이다.**
실제로 이렇게 3개 런(약 20 GPU-시간)을 날렸다.

→ `run_finetune_ikea.sh`에 프리플라이트 체크를 넣었다. 필요 용량을 계산하고 부족하면 거부한다.

### 크래시 후 재개 불가

`--save-only-model`이라 optimizer/scheduler 상태가 없다. 크래시하면 **남은 체크포인트로
스캔은 되지만 학습 재개는 안 된다.** 저장 중 죽은 체크포인트는 샤드가 일부만 있으니
(3개 중 2개) 스캔 전에 확인할 것.

### 잘 틀리는 것들

- **`outputs/<exp>/<exp>/checkpoint-*`** — HF Trainer가 실험명을 한 번 더 중첩시킨다.
- **프로세스 대기 패턴에 후행 공백 필수** — `..._b64`가 `..._b64_torsograv`의 프리픽스다.
- **19차원 런은 `_wa_val`로 채점** — 16차원 val로 채점하면 조용히 다른 값이 나온다.
- **BCT 디렉터리 이름이 내용과 반대** — `_abl`이 채택본(라운드2, 192/15k),
  `_final`이 기각본(라운드3, 256/30k)이다. 배포 모델은 라운드2 **ckpt-15000**.
- **GPU 7은 비워둘 것** (사용자 작업용). `scan_when_done.sh`에 가드가 있다.

## 11. 대회 인터페이스 제약 (`ikea_iros_submit`, 미확정)

확인만 한 상태. 확정되면 배포 코드를 고쳐야 한다.

- **state는 `body_q`(29) + `base_quat`(4)뿐.** 속도 전무 → 속도 블록 ablation은 불가능.
- **그리퍼 state를 못 받는다** (`left_hand_q`는 Dex3용 (7,)이고 Dex1 리그에선 부재).
  의도된 설계이며 문서에 "synthesize하라"고 적혀 있다.
  → 명령값 되먹임으로 대체 가능: 명령 vs 실측 오차가 범위의 **2.0~2.4%**(최대 4.5%)이고,
  닫는 중/유지 중 잔차가 +0.16~0.17로 **거의 일정한 오프셋**이다. 물체에 걸려도 안 벌어진다.
- **action은 관절이 아니라 EE 포즈다.** `decoupled` 레인 `(T,25)`:
  손 2관절 ×2, EE 위치 3 + 쿼터니언 4(**w-first**) ×2, navigate_cmd 3, base_height 1, torso rpy 3.
  IK는 주최측이 돌린다 → 팔꿈치(널스페이스)를 우리가 통제 못 한다.
- 카메라: `ego_view`만 항상 있음. 스테레오는 `camera_keys` opt-in, 손목은 없을 수 있음.

### ✅ 확정 1 — 판정은 "실행 창"에서 해야 한다

처음에 후반 청크(25~40스텝)로 판정하겠다고 세운 기준은 **틀렸다.** 비동기 추론 배포에서는
40스텝 중 지연 보정 후 8개 정도만 실행하고 나머지는 RTC 오버랩에 쓰인다. 실행되지 않는
구간에 가중치를 준 셈이다.

지연 오프셋 `s`부터 8스텝을 실행한다고 보고 다시 계산하면 (팔, vs R1):

| 실행 구간 | R3 | R4 | R2 |
|---|---:|---:|---:|
| 1–8 | −16.7% | −17.2% | +0.6% |
| 3–10 | −14.3% | −14.7% | +0.4% |
| 5–12 | −11.6% | −12.0% | +0.4% |
| 7–14 | −9.2% | −9.6% | +0.4% |
| 9–16 | **−7.3%** | **−7.6%** | +0.5% |

EE 기준도 같은 구간에서 −9.2% → −6.0%로 유지된다. **지연을 비관적으로 9스텝 잡아도
−7% 이상이 남는다.** 전체 40스텝 평균 −4.5%는 배포 가치를 과소평가하는 수치다.

### ✅ 확정 2 — 팔 속도 입력은 채택

세 태스크 전부 같은 부호로 개선된다 (팔 −3.5 / −3.7 / −5.1%, EE8 −9.0 / −5.5 / −11.4%).
그리퍼도 −5.9%로 대역(2.56%) 밖인데, 그리퍼는 팔 관절 속도로 외삽이 **불가능한** 양이므로
속도가 국면 단서(이동 중 / 파지 임박)로도 쓰이고 있다는 뜻이다.

### ✅ 확정 3 — 속도 키 드롭아웃 0.5는 무효 ❌

"속도를 불확실하게 만들어 시각 경로를 살린다"는 의도였다. R4는 R3와 **속도가 있을 때도
없을 때도** 구별되지 않는다.

추론 시 속도를 정규화 후 0으로 만들어(= 데이터셋 평균) 측정한 의존도 (`--zero-state-keys`,
ckpt-20000):

| | 팔 1–8 | EE8 | 그리퍼 |
|---|---:|---:|---:|
| R1 (속도 입력 자체가 없음) | 1.445 | 11.79 | 0.2306 |
| R3 | 1.206 | 10.74 | 0.2182 |
| R3 속도=0 | 1.523 (**+26.3%**) | 12.30 | 0.2371 |
| R4 | 1.200 | 10.57 | 0.2163 |
| R4 속도=0 | 1.506 (**+25.5%**) | 12.11 | 0.2405 |

의존도가 사실상 동일하다(26.3% vs 25.5%). 게다가 **R4를 속도 없이 돌리면 R1보다 4.2%
나쁘다** — 학습 중 절반을 0으로 봤는데도 R1 수준의 무속도 경로를 못 만들었다. 무속도
샘플이 실질 10k 스텝어치뿐이었던 것이 자연스러운 설명이다. **이 노브는 버린다.**

부수적으로 얻은 위험 경계:

- 속도가 정상 작동할 때 이득: **−16.7%** (1.445 → 1.206)
- 속도 신호가 통째로 무의미해지는 최악의 경우 손실: **+5.4%** (1.445 → 1.523)

업사이드가 다운사이드의 3배다.

### ✅ 확정 4 — BCT 웜스타트는 맞교환이다 (§7의 유보 해소)

v1에서 팔·EE8의 부호가 엇갈려 결론을 유보했었다. v2에서는 세 태스크 전부 같은 부호다:

| 태스크 (비중) | 그리퍼 | 팔 | EE8 |
|---|---:|---:|---:|
| insert (26%) | −6.9% | +3.5% | +0.8% |
| pick (26%) | −4.1% | +1.5% | +2.8% |
| rotate (48%) | −12.7% | +0.1% | +2.7% |
| **전체** | **−9.6%** | **+1.2%** | **+2.2%** |

**그리퍼 −9.6%를 얻고 실행 창 팔 정밀도를 내주는 거래**이며, 전반적 개선이 아니다.
그리퍼 이득이 가장 큰 태스크가 다리를 쥐고 있는 `rotate`(−12.7%)인 것은 BCT가 그 상태를
많이 봤다는 해석과 맞지만, 검증하지는 않았다.

§7의 "결론 유보"는 **부호 일관성에 한해** 해소됐다. 어느 쪽을 배포할지는 여전히 실기
문제다 — 지표만으로는 결정할 수 없다는 §7의 결론은 그대로다.

### ⚠️ 미검증 — 폐루프

개루프 스캔은 **정답 속도**를 넣어준다. 배포 폐루프에서는 속도가 모델 자신의 직전 청크가
만들어낸 결과이므로 오차가 되먹임될 수 있다 (copycat / causal confusion). 위 26%는 의존도의
**상한**을 잰 것이지 폐루프 열화를 잰 것이 아니다. 실기 또는 폐루프 시뮬 전에는 확정 불가.

### ✅ 확정 5 — BCT와 팔 속도는 독립적인 효과다

R5(`armvel` config + BCT init), R6(`armvel_bctalign` + BCT init)를 추가로 돌렸다.

| 지표 | R1 | R2 BCT | R3 속도 | R4 속도+KD | **R5 BCT+속도** | R6 정렬본 |
|---|---:|---:|---:|---:|---:|---:|
| 팔 1–8 (deg) | 1.449 | 1.457 | **1.207** | **1.200** | 1.271 | 1.277 |
| 팔 전체 (deg) | 3.299 | 3.338 | 3.152 | **3.140** | 3.230 | 3.216 |
| EE8 (mm) | 11.86 | 12.11 | 10.77 | **10.61** | 11.31 | 11.17 |
| 그리퍼 | 0.2328 | 0.2104 | 0.2191 | 0.2177 | **0.2046** | 0.2095 |
| MSE | 0.0706 | 0.0620 | 0.0649 | 0.0639 | **0.0615** | 0.0634 |

두 효과가 서로의 존재와 무관하게 **각각 두 번씩 같은 방향으로 재현된다:**

| 효과 | 비교 1 | 비교 2 |
|---|---|---|
| BCT init → 그리퍼 ↑, 팔·EE ↓ | R2 vs R1: 그립 −9.6%, 팔 +1.2%, EE8 +2.2% | R5 vs R3: 그립 −6.6%, 팔 +5.3%, EE8 +5.1% |
| 팔 속도 → 팔·EE ↑ | R3 vs R1: 팔 −16.7%, EE8 −9.2% | R5 vs R2: 팔 −12.8%, EE8 −6.6% |

**합쳐도 어느 한쪽을 지배하지 않는다.** R5는 두 축 사이에 놓인다 — 여섯 런 중 그리퍼와 MSE가
최고이고, 실행 창 팔·EE는 R3/R4보다 나쁘다. 맞교환의 위치가 옮겨졌을 뿐 없어지지 않았다.

### ✅ 확정 6 — state 컬럼 정렬도 영향이 없다 ❌

`armvel_config`는 속도를 `right_arm` 뒤에 끼워 넣어 BCT의 뒤쪽 5개 키를 14칸 밀어낸다.
`armvel_bctalign_config`는 속도를 맨 뒤에 붙여 컬럼 0–45를 BCT와 동일하게 유지한다.
R6 vs R5는 **전 지표가 노이즈 대역 안**이다 (팔1-8 +0.5%, 팔 −0.4%, EE8 −1.3%, 그립 +2.4%,
MSE +3.1% / 대역 0.89·1.34·2.56·3.34%).

§7에서 **action head** 슬롯 정렬이 무관하다고 확인했는데, **state 인코더** 컬럼 정렬도
마찬가지다. 웜스타트 이득은 레이아웃이 아니라 그 앞단에서 온다. → 웜스타트할 때 정렬용
config를 따로 만들 필요가 없다.

### 배포 후보 — 2지선다로 좁혀졌다

| | 팔 1–8 | EE8 | 그리퍼 |
|---|---:|---:|---:|
| **R3 `checkpoint-20000`** — 실행 창 최고 | **1.206** | **10.74** | 0.2182 |
| **R5 `checkpoint-20000`** — 그리퍼 최고 | 1.267 (+5.0%) | 11.25 (+4.8%) | **0.2042 (−6.4%)** |

R4는 후보가 아니다. R3와 4개 지표 중 3개가 노이즈이고(팔1-8 −0.57%, 팔 −0.38%, 그립 −0.64%)
EE8만 −1.53%로 대역 1.34%를 겨우 넘는데, **확정 3**에서 기각된 메커니즘을 그 차이 하나로
끌고 갈 이유가 없다. 속도 키 드롭아웃은 목적(무속도 대체 경로 확보)에 실패했고 성능 차이도
사실상 없으므로, 같은 값이면 노브가 없는 R3를 쓴다.

**팔·EE 6%와 그리퍼 6%의 맞교환**이고, 둘 다 노이즈 밖이다. §7에서와 같은 종류의 질문이며
지표만으로는 결정할 수 없다 — 실기에서 무엇이 먼저 실패하느냐의 문제다. 여섯 런 다 16k에서
포화하므로 20k 유지가 맞다.

태스크별 그리퍼는 R5가 `insert` −13.7%, `pick` −21.4%로 크고 `rotate`는 −7.8%로 R2(−12.7%)에
못 미친다. 다만 태스크별 n이 작아 이 순서까지 신뢰하지는 않는다.

## 13. 실기 1차 확인 — R1 vs R2 (BCT 웜스타트)

**결과: 두 모델이 구분되지 않았다.** 개루프에서 그리퍼 −9.6% / 실행 창 EE8 +2.2%로
맞교환이 분명했는데, 실기에서는 "비슷하다"는 정성 관찰이 나왔다.

> 통제된 시행이 아니다. 시행 횟수·성공률·실패 유형을 기록하지 않은 정성 관찰이므로,
> "차이가 없다"가 아니라 **"이 관찰로는 차이를 잡아내지 못했다"**가 정확한 서술이다.

그래도 판단을 바꾸기에는 충분하다. §7과 §12가 유보했던 것은 지표 부족이 아니라
**"이 맞교환을 받을 것인가"**였고, 그건 개루프가 구조적으로 답할 수 없어 실기로 넘긴
질문이었다. 그 실기에서 차이가 보이지 않았다면, 그리퍼 6~10%를 얻으려고 실행 창 팔·EE
2~5%를 내주는 거래에는 근거가 없다.

→ **BCT 웜스타트는 앞으로 쓰지 않는다.** R5/R6도 후보에서 빠지고, 배포 후보는
`armvel` 계열 단독(R3)으로 좁혀진다. 다른 데이터셋으로 옮길 때 §7의 "여기서 일반화하지
말 것"은 그대로 유효하다 — 이번 결과도 n=1이다.

## 14. 30k 완주 — 그리퍼만 26k까지 개선, 팔/EE는 포화 ✅ 확정

v1의 "30k 실패"는 §6 정정대로 미완주였다. v2에서 base와 armvel을 각각 30k 스케줄로
완주시켰다 (eff 64, 코사인 anneal 30k 기준, 체크포인트 15개 전수 스캔).

**20k 스케줄 plateau(16-20k) → 30k 스케줄 후반 plateau(26-30k):**

| | arm8 | EE8 | 그리퍼 |
|---|---:|---:|---:|
| base | +0.2% | +0.9% | **−6.4%** |
| armvel | +1.9% | −0.2% | **−4.4%** |

그리퍼만 대역(2.56%) 밖. 그리퍼는 22k→26k까지 단조 감소 후 평평해진다
(armvel: 0.2158→0.2130→0.2102→**0.2085**→0.2101→0.2097). **실질 포화점은 26k.**

**스케줄 효과 교차 검증**: 같은 20000스텝에서 30k 스케줄이 20k 스케줄보다 arm8
+2.2~2.4% 나쁘다 — LR이 덜 anneal된 상태. v1 관찰(10.85 vs 10.66)과 일치.
30k의 이득은 "더 돌아서"가 아니라 anneal 완주에서 온다.

**속도 입력 효과의 세 번째 재현**: 30k끼리도 armvel이 base 대비 arm8 −15.2%,
EE8 −10.1%.

### 배포 후보 갱신

| | arm8 | EE8 | 그리퍼 |
|---|---:|---:|---:|
| armvel 20k `ckpt-20000` (§12) | **1.206** | 10.74 | 0.2182 |
| **armvel 30k `ckpt-26000`** | 1.224 (+1.5%) | 10.74 (동일) | **0.2085 (−4.4%)** |

EE를 안 내주고 팔 1.5%만 내주는 거래라 §7/§13의 BCT 맞교환(그리퍼 −9.6% ↔ EE8
+2.2%)보다 싸다. 지표상 우세는 30k/26000. 다만 실기에서 그리퍼 −9.6%도 구분되지
않았으므로(§13) −4.4%의 체감은 기대하지 않는 것이 안전하다.

`insert` / `rotate`를 보강할 수 있는지 검증했다. **결론: 이 구성에서는 순손해다.**

### 데이터 준비

원본은 하체 이동이 많은 긴 v3.0 에피소드라 그대로 못 쓴다. `convert_lightwheel_v3_to_v2.py`가
**base가 정지 명령인 구간에서 `insert`/`rotate` 프레임만** 잘라 v2.1 클립으로 뽑는다.

| | 값 |
|---|---|
| 결과 | **913 클립 / 329,270 프레임 / 274.4분 @20Hz** |
| 태스크 비율 | `rotate` 90.3% / `insert` 9.7% |
| state | `joint_position` 33차원 (raw 관절각) |
| action | 16차원 = 양손 2 + 양팔 EE 포즈 14 (전부 ABSOLUTE) |

**태스크별 마스크를 따로 잡는 게 중요했다.** 첫 버전은 원하는 태스크를 한꺼번에 마스킹하고
클립을 다수결 라벨로 붙였는데, `insert`(중앙값 5초)가 `rotate`(30초)로 그대로 이어지는 탓에
**704클립 중 403개가 혼합, 프레임의 7.8%가 오라벨**이 되고 `insert`가 출력의 4.4%로 묻혔다.
경계에서 자르면 라벨이 정확해지고 비용은 seam의 min_frames 미만 토막(~2%)뿐이다.

### 인프라 — embodiment tag 분리

두 소스는 state/action의 의미가 전혀 다르므로 **projector를 공유시키면 안 된다.**
`NEW_EMBODIMENT_2`(슬롯 12)를 새로 만들어 sim에 붙이고, 실취득은 슬롯 10을 유지했다.
공유되는 것은 **DiT와 frozen backbone뿐** — 가설이 "접근하고 접촉에서 멈추는 동작은
도메인 일반적이고 픽셀은 아니다"였으므로 이게 정확히 시험하려던 지점이다.

- `gr00t/data/embodiment_tags.py` — `NEW_EMBODIMENT_2` 추가
- `processing_gr00t_n1d7.py` — `_PROJECTOR_INDEX_GROUPS`에 슬롯 12 등록
- `finetune_config.py` / `launch_finetune.py` — `--mixture-spec` (JSON) + `--mix-ratio`
- `examples/unitree_g1_dex1_ikea/mixtures/ikea_plus_sim.json`

### 두 런 — 배치를 맞춘 단일 변수 비교

sim을 섞으면 스텝당 샘플 수가 바뀌므로, **동일 배치·동일 스케줄의 대조군을 따로 돌려야**
sim 효과와 스케줄 효과가 분리된다.

| | 데이터 | GPU / 배치 | 스텝 | 속도 |
|---|---|---|---|---|
| **C0** (대조군) | IKEA만 | 4×A100, eff 256 (64/GPU × accum 1) | 10k | 3.09 s/it |
| **S1** | IKEA + SIM 1:1 | 동일 | 10k | 3.27 s/it |

plateau(8/9/10k) 평균 ± 자체 편차, R1(§12 기존 레시피)을 같이 둔다:

| 런 | arm8 | EE8 | 그리퍼 |
|---|---:|---:|---:|
| R1 — IKEA만, eff 64 / 20k | **1.449** ±0.16% | **11.86** ±0.50% | 0.2328 ±0.80% |
| C0 — IKEA만, eff 256 / 10k | 1.470 ±0.27% | 11.95 ±0.20% | **0.2238** ±0.30% |
| S1 — IKEA+SIM, eff 256 / 10k | 1.484 ±0.50% | 12.18 ±0.38% | 0.2293 ±0.77% |

### 효과 분해

| | arm8 | EE8 | 그리퍼 |
|---|---:|---:|---:|
| 스케줄 효과 (C0 vs R1) | +1.49% | +0.75% | −3.84% |
| **SIM 효과 (S1 vs C0)** | **+0.95%** | **+1.94%** | **+2.44%** |

**EE8 +1.94%는 대역(0.38%)의 5배**다. sim은 세 지표 전부에서 손해다.
동시에 eff 256/10k 자체도 R1보다 팔·EE가 나쁘다 — 60k 프레임에 배치 256은 과하다는
§2의 판단이 재확인됐다(그리퍼만 −3.8%로 이득).

### ⚠️ 손해가 하필 목표 태스크에 몰린다

| 태스크 | n | arm8 | EE8 | 그리퍼 |
|---|---:|---:|---:|---:|
| `pick table leg` | 180 | −1.1% | +0.3% | +5.5% |
| **`insert table leg to table base`** | 182 | **+6.0%** | **+7.4%** | **−9.5%** |
| `rotate leg to tighten` | 335 | −0.5% | −0.6% | +5.3% |

sim의 `insert`는 전체의 9.7%뿐인데 **그 태스크만 골라 망가뜨렸다.** `pick`/`rotate`는
사실상 무변화다. 조립 방식이 달라 실기 `insert` 궤적을 적극적으로 방해한 것으로 읽힌다.
"구멍 찾기를 보강한다"는 애초 동기와 정반대 방향의 결과다.

### 왜 안 되는가 — frozen 인코더 특징 거리

`tune_visual=False`라 인코더가 sim을 보고 배우는 게 없다. 두 데이터셋 사이 거리를
각자의 내부 스프레드로 정규화해 측정했다 (`datasets/gap_per_view.log`):

| 뷰 | BCT ↔ IKEA | **IKEA ↔ SIM** |
|---|---:|---:|
| ego | 1.89× | **5.21×** |
| 왼손목 | 1.37× | **3.33×** |
| 오른손목 | 1.30× | **3.20×** |

**실데이터끼리(1.3~1.9×)와 sim(3.2~5.2×)은 자릿수가 다르다.** 그리고 그 1.89×짜리
BCT조차 실기에서 무효였다(§13).

### 증강으로 안 좁혀진다 ❌

sim 렌더링에 색/노이즈 증강을 입혀 격차를 좁힐 수 있는지 측정했다
(`datasets/aug_gap.log`, ego 뷰):

| sim 증강 | clean IKEA와의 거리 | 정규화 비 | sim 자체 스프레드 |
|---|---:|---:|---:|
| clean | 0.0645 | 5.28× | 0.0147 |
| jitter (학습 설정) | 0.0662 | 4.96× | 0.0169 |
| jitter ×2 | 0.0773 | 4.81× | 0.0224 |
| heavy DR | 0.0691 | 3.78× | 0.0268 |

**비율이 내려간 건 분자가 줄어서가 아니라 분모가 커져서다.** heavy DR에서 sim 스프레드는
+82%인데 실데이터까지의 절대 거리는 오히려 **+7%** 늘었다(손목 뷰도 −2.7%로 사실상 제자리).
→ 증강은 sim을 real 쪽으로 **옮기지 않고 퍼뜨린다.** 도메인 랜덤화로 이 격차를 지우는 건
이 파이프라인에서 불가능하다.

### 해상도·Hz를 맞추는 것도 답이 아니다

- **해상도**: `image_target_size = [256,256]`로 모든 영상이 리사이즈된다. sim 224×224를
  실기 480×640에 맞출 이유가 없다. 진짜 기하 차이는 **화각/종횡비**(1:1 vs 4:3)다.
- **Hz**: sim 20Hz vs 실기 30Hz. horizon 40을 프레임 수로 맞췄으므로 공유 trunk가
  sim에서는 "40스텝 = 2.0초", 실기에서는 "1.33초"를 배운다. 이건 리샘플로 고칠 수 있지만,
  위의 시각 격차 상한이 남는 한 투자 대비 기대값이 낮다.

### ⚠️ 미검증 — 무엇이 증명되지 않았는가

정직하게 적으면 **"이 구성에서는 해롭다"**이고, "sim이 원리적으로 쓸모없다"는 아니다.

- **mix_ratio 1:1만 시험했다.** 8:1은 다를 수 있다 — 다만 절반을 넣어 손해였으니 소량으로
  이득으로 뒤집힐 가능성은 낮게 본다
- **`rotate`만 넣는 안**을 안 돌렸다. 손해가 `insert` 궤적 불일치 때문이라면 유효할 수 있다
- **자세 정합 후 재렌더링**은 미검증 (허리 10.5°, 손목 yaw 33.5° 어긋남)

### sim 데이터의 남은 용도 — 학습이 아니라 배포 검증

sim action 23차원이 대회 `decoupled` 레인의 `(T,25)`와 **손 자유도만 빼고 동일**하다.
EE 포즈 규약(w-first 쿼터니언), 좌표계, base/torso 슬롯의 실물 샘플이다.
관절 출력을 FK로 EE로 바꾸는 경로(§11)를 만들 때 **정답지로 쓸 수 있다.** 학습 없이 얻는 값이다.

### ⚠️ "aug"라는 말이 두 가지를 가리킨다

런 이름의 `_aug_`는 **이미지 증강이 아니라 state 증강**이다. 헷갈리기 쉬우니 분리해 둔다.

| | 정체 | 판정 |
|---|---|---|
| **augmented state 46차원** | 기존 31 + `base_gravity`(3) + FK EE(12) | ✅ **채택** — BCT 라운드2(`..._bct/EXPERIMENTS.md` §5)에서 6/6 체크포인트 MSE·그리퍼 우세, f5 −3.0%, 팔 동률. **배포 비용 0** (IMU와 팔 관절에서 바로 계산) |
| **이미지 증강** (color jitter + random crop) | 학습 시 픽셀 변형 | ⚠️ **미확정** — ×0.5만 시험했고 노이즈 내. **0으로 끈 런은 없다** |

이미지 증강의 간접 근거: frozen 인코더는 색 변화에 전혀 robust하지 않은데(기본 지터만으로
특징이 자연 변동의 64.5%만큼 이동) 세기를 절반으로 줄여도 성능이 안 변했다
→ **action expert가 시각 특징 노이즈에 병목이 걸려 있지 않다.** 강화도 약화도 무의미.

### ⚠️ joint vs EE action — A/B를 안 했다

**학습으로 비교한 적이 없다.** `G1_Dex1_BCT_subtask_ee`(14차원)는 변환만 하고 학습 보류 상태다.
간접 근거는 joint 쪽이다:

- **REL joint가 ABS joint를 크게 이김** — first-5 MAE −33%, 팔 −11% (`unitree_g1_dex1_bct/EXPERIMENTS.md` §2)
- **FK EE를 state로 넣어도 팔은 동률** — EE 표현 자체가 팔 정확도를 주지 않음
- **배포 비용** — joint는 그대로 명령, EE는 추론 루프에 IK가 들어가 실패 모드가 하나 늘어남

REL joint의 강점이 "예측이 현재 상태에 앵커된다"는 구조적 이점인데, 이건 EE 공간에서
기대하는 이득과 같은 성질이다. 즉 **REL joint가 이미 그걸 가져가고 있어서** 바꿀 유인이 약하다.
단, 대회 `decoupled` 레인은 EE 출력을 요구하므로 그건 **인터페이스 문제**로 따로 푼다(§11).

## 17. rotate table / flip table 추가 — 라벨 실험 준비 (2026-08-26)

`URL-RFM/IKEA_rotatetable{1,2,3}`과 `URL-RFM/IKEA_fliptable`을 기존 세 태스크에 합쳤다.
학습은 진행 중이고, 여기 적는 것은 **학습 없이 확정된 것들과 실험 설계의 근거**다.

### 데이터

| 소스 | ep | 프레임 | 시간 | 내용 |
|---|---:|---:|---:|---|
| `rotatetable1` | 31 | 13,678 | 7.6분 | 다리 1개, 가로→세로 |
| `rotatetable2` | 31 | 13,700 | 7.6분 | 다리 2개, **세로→가로** |
| `rotatetable3` | 31 | 11,430 | 6.3분 | 다리 3개, 가로→세로 |
| `fliptable` | 43 | 26,405 | 14.7분 | 책상 뒤집기 |

전부 v3.0이라 `convert_urlrfm_v3_to_v2.py`로 변환. 병합 결과 **282 ep / 128,200 프레임
(71.2분) / 117,202 H40 윈도우**, val 32 ep. state 86 / action 19로 절단(기존 셋과 폭을
맞추기 위해. torque는 stage1 산출물에 보존).

**셋 다 `base_cmd_vel`이 상수 0** — 정지 취득이라 우리 설정과 일치한다.

### ✅ 확정 — rotate와 flip은 서로 반대 손을 쓴다

| | 왼팔 | 오른팔 | 왼그리퍼 | 오른그리퍼 |
|---|---:|---:|---|---|
| `rotate table` | 40~117° | 15~40° | 능동 | **5.34 고정** |
| `flip table` | 67.6° | **91.3°** | **5.35 고정** | 능동 |
| 기존 3태스크 | 54~73° | 55~73° | 능동 | 능동 |

액션 16차원 중 절반이 각 새 태스크에서 상수다. 모델이 instruction에 따라 한쪽 팔을
정지시키는 것을 배워야 한다는 뜻이고, 동시에 두 새 태스크끼리는 액션 공간에서 겹치지
않는다는 뜻이기도 하다.

### ✅ 확정 — 새 태스크는 기존 태스크들끼리보다 덜 겹친다

frozen 인코더 ego 뷰 거리(자체 산포로 정규화)와, 최근접 이웃이 자기 태스크에서 나오는 비율:

| 태스크 | own-task 검색 성공 | (우연) |
|---|---:|---:|
| `pick table leg` | 95.5% | 21.5% |
| **`insert table leg to table base`** | **77.4%** | 21.1% |
| **`rotate leg to tighten`** | **75.6%** | 21.1% |
| rotate table [set1/2/3] | 93.5 / 94.5 / 99.0% | 12.1% |

| 쌍 | ego 거리 비 |
|---|---:|
| **`insert` ↔ `rotate leg`** | **1.03×** |
| `insert` ↔ `pick` | 1.08× |
| `pick` ↔ `rotate leg` | 1.11× |
| 새 태스크 ↔ 기존 셋 | **1.68~2.09×** |

**진짜 간섭은 이미 안에 있다.** `insert`와 `rotate leg`는 인코더에게 같은 장면(1.03×)이고,
액션 불일치도 자기 태스크(8.14 / 8.77°) 대비 상대(10.52 / 11.61°)가 20~30%밖에 안 높다.
`pick`은 자기 7.43 vs 상대 25~27로 완전히 격리돼 있다.

§5에서 **`rotate leg`가 팔 최악(3.318°), `pick`이 최고(2.585°)**였던 순서와 정확히 맞는다.
인과는 미확정이나 일관되며, 맞다면 rotate leg는 데이터가 아니라 **구분 가능성**의 문제다.

→ 새 태스크를 넣는 것이 기존 조합에 추가하는 간섭은 이미 존재하는 간섭보다 작다.

### ✅ 확정 — 언어 채널은 "무슨 동작"에 강하고 "어느 방향"에 약하다

배포 모델에 같은 관측을 주고 instruction만 바꿔 팔 액션 변화량(40스텝 청크):

| | 변화 | 노이즈 대비 |
|---|---:|---:|
| diffusion 시드만 (바닥) | 0.467° | 1.0× |
| **학습한 다른 문자열로 교체** | **2.770°** | **5.9×** |
| 안 배운 문자열로 교체 | 1.230° | 2.6× |

DiT는 언어를 실제로 읽는다. 단, 안 배운 문자열 넷(`rotate table base`,
`...to portrait`, `...to landscape`, `turn ... clockwise`)은 1.20~1.27°로 뭉쳐 있어
**의미가 아니라 "아는 셋이 아님"으로만 처리**된다 → 분할은 학습을 시켜야 작동한다.

frozen 텍스트 토큰 간 코사인 거리. 사소한 리워딩("it" 추가, "to"→"into")이 **0.0095**로 바닥:

| 쌍 | 거리 |
|---|---:|
| `pick` ↔ `insert` | 0.1442 |
| `pick` ↔ `rotate leg` | 0.1321 |
| `insert` ↔ `rotate leg` | 0.1157 |
| **`rotate table base` ↔ `rotate leg to tighten`** | **0.0564** ⚠️ |
| `to portrait` ↔ `to landscape` | **0.0056** |
| lengthwise/crosswise, away/across, cw/ccw 등 방향 서술 | 0.014~0.045 |
| **`turn the tabletop square` ↔ `spin the crossbars around`** | **0.1056** |

**방향을 서술하는 모든 표현이 붙는다.** 단어를 셋 바꾼 `faces away`/`faces across`도
0.0535였다 — 바꾼 단어 수가 아니라 **의미 거리**가 지배하고, 방향 부사는 pooling에서
지워진다. 동사를 바꿔야 움직이지만(`upend`/`flatten` 0.0918) 그건 수직축 yaw인 실제
동작과 안 맞고 `flip table`과 0.0950으로 충돌한다. 임의 태그(`task alpha`/`bravo`)는
0.0330으로 오히려 나빴다 — 나머지 문자열이 pooling을 지배한다.

→ **서술을 포기하고 무관한 이름을 쓴다.** 문자열이 정해지면 임베딩은 결정적이라
클래스 내 분산이 0이므로, 필요한 것은 설명이 아니라 구분되는 조건이다.

### ⚠️ 미확정 — 시각이 방향을 보는지는 이 데이터로 판정 불가

두 측정이 반대로 나왔다.

| 방법 | 결과 |
|---|---|
| 선형 probe (set1+set2 학습 → set3 테스트) | **65%** (이진, 사실상 못 맞춤) |
| 시각 특징 최근접 이웃 검색 | **89~97%** 자기 세트 (우연 30~35%) |

probe는 세션을 넘어 전이시키는 테스트라 비관적이고, 검색은 세션 내 매칭을 허용하니
낙관적이다. **세 세트가 각각 다른 촬영 세션이라 "책상 방향을 봤다"와 "세션을 알아봤다"를
분리할 수 없다.** 배포 현장에는 맞춰볼 세션이 없다.

처음에 pooling된 특징의 선형 분리도만 보고 "시각이 방향을 못 본다"고 적었던 것은
과했다. 모델이 하는 일은 전역 라벨 분류가 아니라 **어디를 잡을지 찾는 것**이고, mean
pooling은 그 공간 정보를 버린다.

파지 위치는 실제로 갈린다 — 그리퍼가 닫히는 순간의 왼손 EE:

| 쌍 | xyz 분리 (통합 표준편차 대비) |
|---|---|
| set1 vs set3 (같은 방향) | 0.20~0.46 σ — 겹침 |
| set1 vs set2 | **1.29~2.24 σ** |
| set2 vs set3 | **0.93~2.92 σ** |

**다만 파지 위치로 다 설명되지 않는다.** 파지 포즈를 원점으로 정렬한 뒤에도:

| 쌍 | 세트 내 산포 대비 |
|---|---:|
| set1 vs set3 | **0.71×** — 구분 불가 |
| set1 vs set2 | 2.08× |
| set2 vs set3 | 2.58× |

set1/3은 손목을 27~34°까지 돌렸다 제자리로 오는데 set2는 **84°까지 돌려 40° 돌아간 채
끝난다.**

### ✅ 확정 — set 1과 3은 어떤 지표로도 갈라지지 않는다

파지 0.20~0.46σ, 정렬 궤적 0.71×, 상태 기반 최근접 이웃 액션 오차 7.2°(세트 내부 4.1°,
set2 대비 9.8~13.3°). **다리 개수가 2개나 차이 나는데 가장 가깝다** — 방향이 다리 개수보다
2~3배 지배적이다. → 3분할은 어느 결론이 나든 근거가 없다.

### 실행 중인 네 런

전부 **46차원 aug state**(속도 없음 — §11의 대회 boundary가 속도를 안 준다),
action 16차원, eff 64, **30k cosine**, `save_total_limit 8`(16k~30k만 유지), 2 GPU씩 동시.
1.43~1.45 s/it로 §3의 단독 최적값(1.46)과 동일 — 4런 동시에도 저하가 없다.

| 런 | 데이터 | rotate 라벨 | 비교가 답하는 것 |
|---|---|---|---|
| **U** | 전부 | 셋 다 `turn the tabletop square` | — |
| **S** | 전부 | set2만 `spin the crossbars around` | **방향 분할** (U와 27 ep 라벨만 다름) |
| **N** | 전부 | 셋 다 `rotate table base` | **태스크명 거리** (U와 이름만 다름) |
| **X** | 새 태스크만 | `turn the tabletop square` | **기존 데이터의 기여** |
| (대조) | — | 기존 `..._v2` 재스캔 | **기존 태스크 손상 여부** |

대조군을 새로 학습하지 않는 이유: 기존 `g1_dex1_ikea_relarm_3view_aug_b64_v2`가 동일
레시피(eff 64 / 20k / cosine / seed 42 / 같은 46차원 config)라 **재스캔만 하면 된다.**

**X의 교란**: 같은 30k에서 X는 37 epoch, U는 16.4 epoch(윈도우 51,844 vs 117,202).
스텝과 epoch을 동시에 맞출 수 없으므로 X vs U는 "주어진 예산으로 무엇을 학습할 것인가"에
답하지 그 이상은 아니다.

**30k인 이유**: 데이터가 1.79배라 epoch당 1,021→1,831 스텝이다. 배포 모델은 26k=25.5
epoch에서야 그리퍼가 멈췄는데(§14) 20k면 10.9 epoch뿐이다. 30k=16.4 epoch은 절충이고,
"epoch이 옳은 불변량인가"는 미검증이다.

### ⚠️ S가 지면 해석이 갈린다

"분할이 불필요하다"와 "0.1056으로도 방향을 전달하기엔 부족하다"가 구분되지 않는다.
후자라면 조건 신호를 언어가 아니라 state에 넣어야 하는데, 이 실험으로는 거기까지 못 간다.

* **원본에 산발적 디코딩 불가 프레임.** `rotatetable1/cam_left_high` 8753,
  `rotatetable2/cam_right_high` 946. 재인코딩이 은폐해 **잘라낸 클립은 멀쩡**(403프레임
  전수 디코딩 성공, 길이 정확). 검증만 깨지므로 못 읽는 원본 프레임은 건너뛰고 보고한다.
* **정렬 판정은 클립 단위로.** set3에서 46.3/255가 나왔는데 그 클립의 **첫·마지막은 맞고
  중간 하나만 +1에서 맞았다.** 컷은 균일하게만 밀리므로 이건 원본 디코더 흔들림이다.
  세 샘플이 전부 어긋나야 실패로 본다.
* **`--save-total-limit`은 마지막 N개를 남긴다.** §12·§14 어디서도 전반부 체크포인트를
  쓴 적이 없다.
* **`episode_sampling_rate`는 데이터를 버리지 않는다.** 이름과 docstring이 오해를 부르는데,
  실제로는 타임스텝을 셔플해 `1/rate`개 그룹으로 인터리브하고 **전부** shard로 만든다.
  샤딩 입도 노브다. `mix_ratio`도 샘플링 확률이지 제외가 아니다.
* **동시 실행 함정 셋** — ①`run_finetune_ikea.sh`의 디스크 프리플라이트는 런 하나만 보므로
  4런 합계를 런처가 따로 검사한다. ②`examples/finetune.sh`의 `MASTER_PORT` 기본값 29500이
  고정이라 런당 포트를 나눠야 한다. ③런처가 서브셸로 호출되므로 venv를 명시적으로
  활성화해야 한다(`torchrun: not found`로 조용히 죽는다).
* **stats는 config와 무관하다.** `observation.state`/`action` 전체 벡터 기준이고 fingerprint도
  `info.json` 스키마 기반이라, 46차원과 60차원 config가 같은 파일을 공유한다. 다만 4런이
  동시에 생성하려 하면 경쟁하므로 **미리 만들어 둘 것.**

## 18. 라벨 실험 결과 — 분할도 개명도 불필요 ✅ 확정 (2026-08-26)

### ❌ 확정 1 — 방향 분할은 해롭다

### ❌ 확정 2 — 태스크명 거리는 학습 후 무관하다

### 운영 메모 — 스캔이 10배 느렸던 이유

BLAS가 코어 수만큼 스레드 풀을 잡아 **프로세스당 331 스레드 / 1,200% CPU**, 8개 동시에서
**load 268 / 96코어**, GPU는 0~14%로 굶었다. 스캔은 윈도우마다 FK를 80회(체크포인트당
12만 회) 부르므로 이 경로가 핫패스다.

**`OMP_NUM_THREADS=4`로 제한하니 체크포인트당 59분 → 5.9분.** 10배다. GPU 사용률은
14%→26%로 두 배밖에 안 올랐는데 벽시계는 10배 빨라졌다 — 손실의 대부분이 OMP 배리어
스핀이었고 **사용률 지표에는 잡히지 않았다.** 학습 런처는 처음부터 이걸 설정했고 스캔
경로만 빠져 있었다.

## 19. mix_ratio 가중 + arm velocity — 진행 중 (2026-08-26 21:31 기동)

§18의 `insert` 손해(EE8 +12.1%)에 대응하고, 대회 규정이 풀릴 경우를 대비해 속도 포함본을
같이 만든다.

| 런 | GPU | config | 데이터 | 답하는 것 |
|---|---|---|---|---|
| **m16** | 0,1 | 46차원 | 기존×**1.6** + 새×1.0 | `insert` 회복 |
| **m30** | 2,3 | 46차원 | 기존×**3.0** + 새×1.0 | 비율 상한 |
| **uv** | 4,5 | **60차원 armvel** | 병합(자연 비율) | 속도 포함본 |
| **mv** | 6,7 | **60차원 armvel** | 기존×1.6 + 새×1.0 | 조합 |

대조군은 학습하지 않는다 — 46차원은 `..._v2/checkpoint-20000`, 60차원은
`..._v2_armvel/checkpoint-20000`이 각각 동일 레시피(eff 64 / 20k / cosine / seed 42)의
기존 3태스크 전용 모델이라 재스캔만 하면 된다.

### 비율을 1.6으로 고른 이유

`weight = relative_length × mix_ratio` (`factory.py:105`)이므로:

| `--mix-ratio` (기존 셋) | 비중 | 30k에서 받는 epoch |
|---:|---:|---:|
| 1.0 (자연) | 55.8% | 16.4 — U가 이랬다 |
| **1.6** | 66.9% | **19.6** — ctl과 동일 |
| 3.0 | 79.1% | 23.2 |

1.6은 임의값이 아니라 **ctl이 받았던 epoch을 정확히 복원**하는 값이다. 3.0을 같이 돌리는
것은 하나만 시험해 실패하면 "비율이 부족했나"를 못 가리기 때문이다.

### ⚠️ 기대치는 낮다

§18에서 `insert`는 22k~30k 동안 EE8 +0.30%로 평평했다 — **굶은 게 아니라 포화했다.**
mix_ratio는 희석만 다루므로, 원인이 간섭이면 효과가 없다. 그럼에도 돌리는 이유는
`insert` 추가 취득 전까지의 임시 수단이고 GPU가 비어 있기 때문이다.

**근본 해법은 `insert` 에피소드 추가 취득이다** — 노출과 새 궤적을 동시에 늘린다.

### ⚠️ 교란 — 가중은 정규화 통계도 함께 옮긴다

m16/m30/mv는 데이터셋 2개를 mixture 경로로 먹이고 U는 같은 에피소드를 1개로 병합해
먹였다. 비율 1.0이면 샘플링은 동등하지만 `merge_statistics`가 **정규화 통계도 같은
가중치로 섞는다**(`sharded_mixture_dataset.py:270-300`). 즉 가중을 주면 통계가 기존
데이터 쪽으로 이동하고, 이 두 변화는 분리되지 않는다.

### 운영

`mix_ratio`도 `episode_sampling_rate`도 **데이터를 버리지 않는다.** 전자는 어느 데이터셋의
shard를 다음에 뽑을지의 확률이고, 후자는 타임스텝을 인터리브해 shard로 나누는 입도 노브다.
자세한 것은 `mixtures/README.md`.

## 21. pick + insert 병합 — 진행 중 (2026-08-27 23:14 기동)

실기에서 `pick table leg` → `insert table leg to table base` **전환이 이어지지 않는다**는
보고. 두 라벨은 하나의 연속 동작을 자른 것이므로 되돌린다.

### 원본은 연속 비디오 2개다

| 파일 | 비디오 프레임 | 에피소드 길이 합 | 커버 |
|---|---:|---:|---|
| `file-000` | 42,943 | 42,943 | `[0, 42943)` |
| `file-001` | 36,262 | 36,262 | `[0, 36262)` |

**버려진 프레임이 없다.** 에피소드 경계는 스플라이스가 아니라 라벨 절단이다.
(카메라별로 파일 분할 지점이 다르다 — `cam_left_high`는 ep90, `cam_right_high`는 ep99에서
갈린다. 이것 때문에 단순 타임스탬프 검사가 ep99를 오탐한다.)

### 자르면 왜 손해인가

`get_effective_episode_length = length − horizon + 1`이고 `allow_padding=False`
(`data_config.py:98`, 우리 config는 덮어쓰지 않는다). 즉 **모든 에피소드의 마지막
39프레임은 윈도우 시작점이 될 수 없다.** `pick`을 잡는 순간에서 자르면
"막 잡았다 → 들어올려 base로" 구간에 지도 신호가 **아예 없다.**

### 그러나 전부 이어붙일 수는 없다

실패해서 재시도한 지점도 잘려 있다. 프레임 수로는 구분되지 않지만 **state로는 보인다** —
각 차원이 에피소드 *내부*에서 한 프레임에 움직인 최대치를 넘는 점프:

| | 값 |
|---|---|

### instruction — `pick and place the table leg`

frozen backbone 텍스트 토큰 코사인 거리, 남는 태스크들과의 **최솟값**
(기준선: 간섭이 확인된 `insert`↔`rotate leg` = 0.1447):

| 후보 | 최소 | 상대 |
|---|---:|---|
| pick up the table leg and insert it into the table base | 0.172 | rotate leg |
| **pick and place the table leg** | **0.164** | rotate leg |
| pick and insert the table leg | 0.149 | rotate leg |
| assemble the table leg | 0.135 | turn |

병합은 라벨 공간을 좁히지 않는다 — 더 가까웠던 `insert`를 **없애므로 오히려 넓힌다.**

### 런

| 런 | GPU | config | state | 데이터 | 대조군 |

| **p** | 0,1 | relarm_3view_aug | 46 | `..._pnp` | alltask **u** |

30k / SAVE_TOTAL_LIMIT 8 (pvt는 디스크 때문에 5)는 u/uv의 체크포인트 격자를 재현해
best-vs-best가 아니라 체크포인트 대 체크포인트로 비교하기 위한 것이다.

**라벨만 바꾼 팔(arm)은 일부러 뺐다** — instruction 효과를 윈도우 효과와 분리해 값을
매기지만, 어느 쪽 결과든 병합본을 배포하므로 여기서는 사는 게 없다. 필요해지면
`--merge-label-only`가 남아 있다.

2 GPU/런인 이유: NVLink가 없어 고정 effective batch에서 4 GPU가 2.24 s/it, 2 GPU가
1.46 s/it (§3). 8개로 펴는 것보다 빠르다. 실측 1.45 s/it, 30k에 ~12h.

### torque (pvt)

`URL-RFM/IKEA_table_assembly_torque`는 같은 178에피소드·같은 비디오의 재export다 —
`state[:86]`과 `action[:19]`이 **비트 동일**하고 torque 31차원과 `arm_tauff` action
14차원이 붙었다. rotate/flip 소스도 이미 117차원이라 zero-fill이 필요 없다.
비디오가 같아 `--link-clips-from`으로 클립을 재인코딩 없이 하드링크했다.

**넣은 것:** `left_arm_torque`, `right_arm_torque` (60 → 74).
기존 60차원에서 R² 0.65/0.68만 복원된다 — torso_gravity(99.85% 복원 → 기각)와 다르다.

**뺀 것:** 그리퍼 torque(87~88% 복원, 게다가 이 런의 판정 지표라 접촉 신호를 넣으면
측정이 망가진다 — armvel이 그리퍼 *속도*를 뺀 것과 같은 이유), waist torque(89% 복원),
legs torque(걷지 않는 로봇의 지지 하중).

**⚠️ 지름길이 열린다.** 위치 제어 팔의 관절 토크는 서보 오차 ≈ 상대 목표라서 velocity보다
직접적으로 답을 흘린다. 상대 좌팔 목표의 선형 R²:

| horizon step | 1 | 4 | 8 | 16 | 28 | 40 |
|---|---:|---:|---:|---:|---:|---:|
| arm_vel | 0.40 | 0.62 | 0.60 | 0.41 | 0.23 | 0.14 |
| arm_torque | **0.59** | 0.34 | 0.20 | 0.11 | 0.07 | 0.07 |
| 둘 다 | 0.86 | 0.83 | 0.69 | 0.45 | 0.27 | 0.20 |

torque의 유출은 **h=1에 집중되고 빠르게 사라진다**(velocity는 h=4~8에서 최대 —
배포가 실제로 실행하는 구간이다). 실행 구간 8스텝 기준 torque가 얹는 것은 R² 약 9포인트.
**§14와 같은 규칙으로 판정한다 — 후반 chunk와 그리퍼로 보고, 첫 8스텝 팔 오차로 보지 않는다.
step 1~4에서만 나타나는 이득은 실력이 아니라 지름길이다.**

`arm_tauff`(action 19~33)는 **쓰지 않았다** — 관측이 아니라 다른 action space이고,
배포 측이 토크 명령을 받아야 한다.
