# IKEA table assembly — 실험 기록

대상: `carroll511/IKEA_table_assembly` (G1 + Dex1, `teleop_ikea.py` 녹화, 제자리 양팔 조립)
자매 실험: `examples/unitree_g1_dex1_bct/EXPERIMENTS.md` (BCT 데이터셋). 레시피 대부분을 여기서 가져왔다.

---

## 0. 데이터셋

| | |
|---|---|
| 원본 | LeRobot **v3.0**, 276 ep / 66,600 frame @ 30 fps = 37분 |
| 서브태스크 | `pick table leg` 77ep · `insert table leg to table base` 72ep · `rotate leg to tighten` 127ep |
| 카메라 | `cam_left_high` `cam_right_high` `cam_left_wrist` `cam_right_wrist` — 640×480 AV1, 4개 모두 정확히 66,600 프레임 |
| state / action | 86차원(18블록) / 19차원(5블록) |

### 확인된 사실

- **`base_cmd_vel` 3차원이 전 프레임 정확히 0** (std 0.000000). 로코모션 미사용 → action에서 제외.
  정규화 시 q01=q99가 되어 0으로 나눈다.
- **action에 waist가 없다.** `teleop_ikea.py`는 팔만 명령하고 waist는 시작 자세 유지(에피소드 내 0.09~0.45°).
- **legs도 거의 안 움직인다** (에피소드 내 0.73°). 제자리 작업.
- **스톨이 이미 제거돼 있다** (|Δarm| < 1e-4가 0.07%). BCT에서는 직접 청소해야 했다.
- **타이밍이 완벽하다.** dt 33.333ms 고정, gap 0, frame_index 불연속 0.
- **action-state lag는 2~3프레임**(1.05°). IK+제어 지연으로 정상.
- **`left_eef`/`right_eef`는 같은 행 관절의 FK이고 lag이 0이다.**
  `FK(arm_q[t], waist=0)` vs 저장값 오차 **4.2e-09 m** (lag ±1에서는 6e-4).
  BCT의 기록 ee_state가 10프레임 지연이라 재계산해야 했던 문제가 여기엔 없다.
  URDF sha256 `8bbf0066…c238735`가 로컬 파일과 일치, 배포 코드 `G1WristKinematics`가
  **1.5e-08 m / 5.9e-08 rad**로 재현.
- **스테레오 좌우 명명이 맞다.** `cam_left_high`의 특징점이 `cam_right_high`보다 오른쪽에 찍힘
  (15개 샘플 전부 같은 부호). BCT에서 cam_0/cam_1이 뒤집혀 있던 것과 달리 이름을 믿어도 된다.

### 원본 데이터셋이 이미 적용한 필터

`modality.json`의 `_ikea.notes.filters`에 기록돼 있다. **우리 변환은 아무것도 버리지 않는다**
(276 ep / 66,600 frame 손실 0, state/action 바이트 동일).

| 필터 | 값 |
|---|---|
| `head_trim_s` | 2.0 (녹화 앞 2초 삭제) |
| `min_static_run` / `static_eps_rad` | 15 / 1e-6 (텔레옵 스톨 제거) |
| `max_ik_residual_mm` | 20.0 |
| `require_motion_data_ready` | True |
| `min_segment_len` | 40 (horizon과 같음 — 이보다 짧으면 윈도우 0개) |
| `max_frame_gap_ratio` | 2.5 |
| `drop_unlabeled` | True |

필터를 바꾸려면 원본 녹화에서 `convert_ikea_json_to_lerobot.py`를 다시 돌려야 한다.
HF 데이터셋만으로는 잘린 부분을 되살릴 수 없다.

## 1. 변환과 분할

`convert_ikea_v3_to_v2.py` — v3.0 → v2.1 순수 재배치.

**영상은 재인코딩한다(stream copy 아님).** 소스가 AV1 GOP 2라 copy는 홀수 프레임에서 시작하는
에피소드를 앞 키프레임으로 당긴다. **276개 중 146개가 홀수 시작**이라 절반 이상이 조용히
1프레임 어긋났을 것이다. `-ss` + `-frames:v`로 자르면 프레임 정확하고, GOP 2라 비용은
카메라당 1패스 수준. 검증: 144프레임 픽셀 비교 최대 오차 1.7/255.

### val은 세션 단위로 뺀다

연속 에피소드는 같은 촬영 세션(발 위치·헤드 틸트 동일)이라 **랜덤 분할하면 val이 학습 이웃과
거의 중복돼 과적합을 못 잡는다.** 발 위치와 헤드 틸트가 동시에 점프하는 지점으로 27개 세션을
검출하고(`sessions.json`), 그중 4개(3, 12, 19, 23)를 통째로 뺐다.

| | ep | frame | 비율 |
|---|---|---|---|
| train | 250 | 59,589 | 89.5% |
| val | 26 | 7,011 | **10.5%** |

태스크별 val 비율 9.9~11.3%로 균형. 헤드 틸트가 ep85에서 ~7°→~16°로 바뀌는 두 리그 구성이
있는데 양쪽 모두 포함시켰다 (train 4.4~17.6° / val 5.3~17.6°).

## 2. 확정 레시피

BCT 최종본을 그대로 가져오되 **스케일만** 바꿨다.

| | 값 | 근거 |
|---|---|---|
| 뷰 | 3 (`cam_left_high` + 양 손목) | BCT 뷰 개수 ablation에서 4번째 뷰가 팔 정확도 변화 0.00% |
| state | 46차원 9키 | BCT 46차원 키가 이름·차원 그대로 전부 존재 |
| action | **16차원** — 팔 7+7 REL, 그리퍼 1+1 ABS | waist 없음, `base_cmd_vel` 제외 |
| horizon | 40 = 1.33s @30Hz | BCT 검증값. 배포는 앞 8스텝만 실행 |
| **effective batch** | **64** (global 16 = 8/GPU × accum 4) | CK-Sung 실배포 선례(17k프레임/eff 64) |
| max_steps | 20,000 = 25.7 epoch | 아래 3번 |
| save_steps | 2,000 | 스캔용 |
| lr / scheduler | 1e-4 / cosine, warmup 0.05 | 저장소 기본 |
| weight decay | 1e-5 | 기본 |
| state_dropout | 0.2 | BCT 검증값 |
| color jitter | 0.3 / 0.4 / 0.5 / 0.08 (기본값) | 아래 5번 |

학습 데이터: 250 ep / 59,589 frame / **49,839 horizon-40 윈도우** → eff. batch 64에서 **779 step/epoch**.

배치가 64인 이유: 60k 프레임에서 192면 epoch당 260스텝, 256이면 195스텝뿐이다.
BCT(500k)에서는 이 문제가 없어 192를 썼다.

## 3. GPU 수 — 2장이 4장보다 빠르다 ✅ 확정

effective batch 64 고정, 각 30스텝 측정 (s/step, 정상 구간):

| 구성 | bf16 통신 없이 | **`--ddp-comm-bf16`** |
|---|---:|---:|
| 1 GPU (micro 8 × accum 8) | 2.46 | — |
| **2 GPU (global 16 × accum 4)** | 1.55 | **1.46** ← 최적 |
| 4 GPU (global 32 × accum 2) | 3.98 | 2.24 |

배치를 고정하면 GPU를 늘려도 스텝당 일이 늘지 않고 같은 64샘플을 더 잘게 쪼갤 뿐인데,
1.62B 파라미터 all-reduce는 스텝당 한 번 그대로 들고 피어가 늘수록 비싸진다.
이 호스트는 NVLink가 없어 PCIe/SYS를 탄다.

**bf16 압축이 2 GPU에선 6% 이득인데 4 GPU에선 44%**인 것이 통신 병목의 결정적 증거다.
워커를 16→8로 줄여도 4 GPU는 3.98→3.95라 CPU 경합이 아니다.

→ **남는 GPU는 병렬 ablation에 쓴다.** 2 GPU 런 3개를 동시에 돌려도 1.43~1.45 s/it로
속도 저하가 없었다 (96코어에 워커 32+20+20).

**항상 `--use-ddp --ddp-comm-bf16`을 붙일 것.**

## 4. 체크포인트 선정 — eval_loss 쓰지 말 것

BCT에서 확립된 것과 동일. `eval_loss`는 랜덤 노이즈 레벨에서의 flow-matching 회귀 목적함수라
액션 품질을 추적하지 않는다. 대신 `scan_ikea.py`로 open-loop 스캔한다.

**stride를 10으로 낮춘다.** `eval_val_mse.py`의 기본은 stride=horizon(비중첩)이라 이 val에서
윈도우가 164개뿐인데, 체크포인트 간 차이가 1~2%라 노이즈에 묻힌다. stride 10이면 **614개**.
윈도우가 겹쳐 독립 표본은 아니지만, 모든 체크포인트를 **동일한 고정 세트**에 윈도우별 고정
diffusion seed로 채점하므로 *비교*에는 충분하다.

### 노이즈 대역 (baseline 자신의 16k/18k/20k 편차)

| 지표 | 편차 |
|---|---|
| MSE | **2.02%** |
| 팔 | 0.36% |
| EE8 | 0.94% |
| 그리퍼 | 4.87% |

**이보다 작은 차이는 차이가 아니다.** 이 표가 아래 모든 판정의 기준이다.

### ⚠️ MSE는 action 차원이 다르면 비교 불가

19차원 런(waist 포함)의 MSE는 16차원 런과 직접 비교할 수 없다. waist가 거의 상수라 예측이
쉽고, 그 3차원이 평균에 섞여 MSE를 **희석**시킨다. C3 vs baseline의 "MSE −12.8%"가 그 예로,
팔·EE8·그리퍼는 오히려 전부 나빠졌다. **차원이 다르면 팔·EE8·그리퍼로만 비교할 것.**

## 5. 기각된 ablation ❌

모두 20k, effective batch 64, 다른 변수 동일. 기준은 baseline @20000
(MSE 0.02870 / 팔 2.895° / EE8 10.62mm / 그리퍼 0.1290).

| 실험 | 결과 | 판정 |
|---|---|---|
| **`torso_gravity` 추가** (state 46→49) | MSE +5.4%, 팔 +0.8%, EE +1.0%, EE8 +1.7%, 그리퍼 +0.5% — **전 지표 열세** | ❌ |
| **color jitter ×0.5** | MSE +0.6%, 팔 +0.6%, EE8 +2.4% — 노이즈 내 | ❌ |
| **웜스타트 연장** (20k→30k) | 22k에서 MSE **+10.5% 열화**, 회복에 6,000스텝, 최종 배포지표 +0.1% | ❌ |
| **새 30k cosine** | 24k 지점이 baseline과 MSE 동률, 팔·EE8·그리퍼 1~3% 열세 | ❌ |
| **태스크 재밸런싱** | 미실시 — 아래 근거로 불필요 | ❌ |

### `torso_gravity`가 실패한 이유 (사전 예측과 일치)

처음엔 "헤드 카메라 자체 기울기이고 BCT엔 없던 신호"라고 판단했으나 **틀렸다.**
몸통 기울기는 waist **pitch**(범위 10.87°)에서 오는데 그건 이미 `waist`에 있다.
`base_gravity` + `waist`로 회귀하면 **R² 0.9985, 잔차 평균 0.15° / 최대 0.66°**
(전체 스프레드 15.1° 대비). 새 정보가 아니라 중복 3차원이었다.
BCT에서 FK EE가 "정보량 0의 재파라미터화"였던 것과 같은 함정.

배포 가능 여부와는 별개다 — 대회 boundary는 torso IMU를 안 주지만 `base_quat` + `waist`로
복원되므로 만들 수는 있다. 다만 만들 이유가 없다.

### color jitter — 세기가 성능과 무관하다

frozen 인코더(`tune_llm=False`, `tune_visual=False`) 특징이 augmentation으로 얼마나 움직이는지
측정했다. "서로 다른 에피소드 프레임 간 거리"를 100%로 두면:

| 변형 | 기준 대비 |
|---|---:|
| 랜덤 크롭 89.8%만 (기본) | 57.0% |
| **컬러 지터 ×1.0만 (기본)** | **64.5%** |
| 컬러 지터 ×1.5만 | 78.0% |
| 컬러 지터 ×3.0만 | 139.2% |
| **크롭 + 지터 ×1.0 (현재 전체)** | **78.1%** |

인코더는 색 변화에 **전혀 robust하지 않다** — 기본 설정만으로도 특징이 자연 변동의 64.5%만큼
움직인다. 그런데 세기를 절반으로 줄여도 성능이 노이즈 내에서 안 변했다.
→ **action expert가 시각 특징 노이즈에 병목이 걸려 있지 않다.** 강화도 약화도 의미 없으니
기본값을 쓴다. (이건 VLM 튜닝의 기대치를 낮추는 간접 증거이기도 하다.)

### 웜스타트가 실패한 이유

이 런들은 `--save-only-model`로 저장하므로 `optimizer.pt` / `scheduler.pt` / `rng_state.pth`가
**없다.** 게다가 완주한 cosine은 LR을 ~1e-12까지 소멸시킨다. 그대로 재개하면 스케줄러가
새 max_steps 기준으로 재생성되어 **LR이 2.7e-5로 점프**하고 Adam 모멘트는 0에서 시작한다.
LR을 2e-5로 낮춰 통제해도 22k에서 10.5% 열화를 겪었다.

→ **긴 스케줄이 필요하면 처음부터 그 길이로 돌릴 것.** 이어붙이지 말 것.

### 태스크 불균형은 원인이 아니다

학습 윈도우 비율: `rotate` 49.8% / `insert` 28.2% / `pick` 22.0% (최대/최소 2.26배).
BCT는 재밸런싱해서 1.20배였다.

그런데 baseline @20000의 태스크별 성능은:

| 태스크 | 윈도우 | 팔 | EE | EE8 | 그리퍼 | 손목 이동 | EE/이동 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `pick table leg` | 142 (22.0%) | **2.585°** | **16.57** | **8.16** | 0.1845 | 44.2 | **0.38** |
| `insert table leg to table base` | 179 (28.2%) | **2.447°** | 16.59 | 11.66 | **0.1065** | 32.0 | 0.52 |
| `rotate leg to tighten` | 293 (49.8%) | 3.318° | 21.05 | 11.17 | 0.1158 | 50.6 | 0.42 |

**학습 비중이 가장 낮은 `pick`이 팔·EE에서 가장 좋고, 가장 높은 `rotate`가 가장 나쁘다.**
데이터 양이 아니라 과제 난이도가 지배한다 → 재밸런싱할 근거 없음.
60k에서 27%를 버릴 이유가 없다.

`insert`는 EE/이동거리 비가 0.52로 가장 나쁘다 — 손목이 32mm 움직이는 동안 16.6mm를 틀린다.
정밀 삽입이 실제로 제일 어렵다는 것이 수치로 확인된다.

## 7. BCT 사전학습 — ⚠️ **부분적, 결론 유보**

BCT 최종 배포 모델(`RooibosT/gr00t-n1.7-g1-dex1-bct-relarm-aug-30hz-h40`,
라운드2 ckpt-15000, eff. 192 / 15k)에서 웜스타트하면 나아지는가?

**동기**: IKEA의 태스크 문자열 3개가 BCT 5개의 **정확한 부분집합**(글자 단위 동일)이고,
state 46차원 9키가 이름·차원 그대로 같으며, 시각 격차도 작다 (frozen 인코더 특징 거리:
IKEA↔BCT가 IKEA 내부 편차의 1.33~1.47배). BCT는 8배 크다 (500k vs 60k).

**설계**: action 슬롯 정렬 교란을 분리하기 위해 2×2로 돌렸다. BCT는
`[waist3|left_arm7|right_arm7|grip|grip]` = 19차원을 출력하므로, IKEA를 16차원으로 두면
모든 팔 슬롯이 3칸 밀린다. `make_waist_action_variant.py`로 waist를 앞에 붙인 19차원 변형을
만들어 정렬본을 준비했다 (waist는 명령값이 없어 같은 행의 측정 waist를 쓴다).

### 결과 — 16k/18k/20k 평균 ± 표준편차

| 런 | init | action | 팔 (deg) | EE8 (mm) | 그리퍼 |
|---|---|---|---:|---:|---:|
| baseline | base | 16d | 2.900 ± 0.004 | **10.66 ± 0.04** | 0.1314 ± 0.0028 |
| C3 | base | 19d | 2.938 ± 0.012 | 10.78 ± 0.08 | 0.1317 ± 0.0007 |
| C1 | **BCT** | 16d | 2.904 ± 0.007 | 10.74 ± 0.01 | **0.1235 ± 0.0032** |
| C2 | **BCT** | 19d | 2.905 ± 0.005 | 10.76 ± 0.02 | **0.1228 ± 0.0009** |

### ✅ 확실한 것

**1. action head 슬롯 정렬은 최종 성능에 영향이 없다.** C2 vs C1 (BCT init 고정):

| 지표 | 차이 | 노이즈 | 판정 |
|---|---:|---:|---|
| 팔 | −0.03% | 0.30% | 동률 |
| EE8 | −0.21% | 0.21% | 경계 |
| 그리퍼 | +0.56% | 2.71% | 동률 |

초기 loss는 정렬 0.31 vs 어긋남 0.62로 **2배** 차이였는데 20k에서 완전히 수렴했다.
사전학습 이득은 action head가 아니라 그 앞단(state 인코더·백본 어댑터·DiT)에서 오고,
action head는 어차피 처음부터 다시 학습된다.

→ **BCT를 16차원으로 재학습할 필요가 없다.** 정렬을 위해 waist를 끼워 넣을 필요도 없다.

**2. 그리퍼가 −6% 개선되고, 이것은 두 번 독립적으로 재현된다.**

| 비교 | 그리퍼 | 변화량 vs 노이즈 |
|---|---:|---|
| C1 vs baseline (16차원끼리) | **−6.0%** | 0.0079 vs 0.0042 → 유의 |
| C2 vs C3 (19차원끼리) | **−6.7%** | 0.0089 vs 0.0011 → 유의 |

서로 다른 action 공간, 서로 다른 학습 런에서 같은 크기로 나온다.

### ⚠️ 애매한 것 — 그래서 결론을 유보한다

**팔과 EE8에는 이득이 없고, 오히려 나빠진 신호가 있다.**

| 비교 | 팔 | EE8 |
|---|---:|---:|
| C1 vs baseline (16차원끼리) | +0.1% (노이즈 내) | **+0.8% (유의, 악화)** |
| C2 vs C3 (19차원끼리) | −1.1% (유의, 개선) | −0.2% (노이즈 내) |

**두 비교의 부호가 서로 반대다.** 팔은 한쪽에서 개선, 다른 쪽에서 노이즈 내.
EE8은 한쪽에서 **악화**(유의), 다른 쪽에서 노이즈 내. 일관된 방향이 없다.

배포에서 실제로 실행하는 구간이 EE8이므로, 이건 무시할 수 없는 불확실성이다.

**추가로 유보하는 이유:**

- **n=1이다.** 소스 데이터셋 하나(BCT), 타깃 하나(IKEA), 시드 하나. 다른 데이터셋 쌍에서
  같은 결과가 나온다는 근거가 없다.
- **MSE 수치를 신뢰하지 말 것.** C2의 "MSE −21.2%"는 그리퍼 실개선과 waist 희석이 겹친 값이다.
  19차원과 16차원의 MSE는 비교 불가다 (4번 경고 참조).
- **그리퍼 −6%의 해석이 미확정.** BCT가 같은 3개 태스크를 500k 프레임으로 봐서 파지 타이밍을
  배웠다는 것이 자연스러운 설명이나, 검증하지 않았다. 언어 조건부가 같은 문자열이라
  모드 매칭이 쉬웠을 가능성도 있다.

### 현재 판단

**그리퍼 −6% vs EE8 +0.8%의 맞교환이다.** 둘 다 노이즈 밖이라 진짜 트레이드오프이고,
어느 쪽이 나은지는 실기에서 무엇이 먼저 실패하느냐에 달렸다. 지표만으로 결정할 수 없다.

- 파지 유지가 중요한 작업(`insert`, `rotate`)이 많다면 → C1
- 팔 정밀도 우선이면 → baseline

**다른 데이터셋으로 옮길 때는 이 실험을 다시 해야 한다.** 여기서 "BCT 사전학습이 좋다"를
일반화하지 말 것.

## 9. 운영 메모

### 디스크

체크포인트가 **12GB/개**다. `--save-only-model`이어도 3.14B 전체 모델을 매번 쓴다.
20k/2k 런 하나가 120GB를 먹고, 5개 런을 동시에 돌리면 디스크가 조용히 찬다.
**첫 증상은 몇 시간 뒤 저장 중 `SafetensorError: No space left on device`로 런이 죽는 것이다.**
실제로 이렇게 3개 런(약 20 GPU-시간)을 날렸다.

→ `run_finetune_ikea.sh`에 프리플라이트 체크를 넣었다. 필요 용량을 계산하고 부족하면 거부한다.

### 크래시 후 재개 불가

`--save-only-model`이라 optimizer/scheduler 상태가 없다. 크래시하면 **남은 체크포인트로
스캔은 되지만 학습 재개는 안 된다.** 저장 중 죽은 체크포인트는 샤드가 일부만 있으니
(3개 중 2개) 스캔 전에 확인할 것.

### 잘 틀리는 것들

- **`outputs/<exp>/<exp>/checkpoint-*`** — HF Trainer가 실험명을 한 번 더 중첩시킨다.
- **프로세스 대기 패턴에 후행 공백 필수** — `..._b64`가 `..._b64_torsograv`의 프리픽스다.
- **19차원 런은 `_wa_val`로 채점** — 16차원 val로 채점하면 조용히 다른 값이 나온다.
- **BCT 디렉터리 이름이 내용과 반대** — `_abl`이 채택본(라운드2, 192/15k),
  `_final`이 기각본(라운드3, 256/30k)이다. 배포 모델은 라운드2 **ckpt-15000**.
- **GPU 7은 비워둘 것** (사용자 작업용). `scan_when_done.sh`에 가드가 있다.

## 11. 대회 인터페이스 제약 (`ikea_iros_submit`, 미확정)

확인만 한 상태. 확정되면 배포 코드를 고쳐야 한다.

- **state는 `body_q`(29) + `base_quat`(4)뿐.** 속도 전무 → 속도 블록 ablation은 불가능.
- **그리퍼 state를 못 받는다** (`left_hand_q`는 Dex3용 (7,)이고 Dex1 리그에선 부재).
  의도된 설계이며 문서에 "synthesize하라"고 적혀 있다.
  → 명령값 되먹임으로 대체 가능: 명령 vs 실측 오차가 범위의 **2.0~2.4%**(최대 4.5%)이고,
  닫는 중/유지 중 잔차가 +0.16~0.17로 **거의 일정한 오프셋**이다. 물체에 걸려도 안 벌어진다.
- **action은 관절이 아니라 EE 포즈다.** `decoupled` 레인 `(T,25)`:
  손 2관절 ×2, EE 위치 3 + 쿼터니언 4(**w-first**) ×2, navigate_cmd 3, base_height 1, torso rpy 3.
  IK는 주최측이 돌린다 → 팔꿈치(널스페이스)를 우리가 통제 못 한다.
- 카메라: `ego_view`만 항상 있음. 스테레오는 `camera_keys` opt-in, 손목은 없을 수 있음.
